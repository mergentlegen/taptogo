## Подтверждённые дефекты

P1 — исправить до клиентского запуска. P2 — существенная ошибка функций или защиты, исправить до платного пилота.

### F01 · P1 · Демо-пароль работает в production, включая SUPER_ADMIN

**Код:** `src/server/container.ts:87`, `src/server/auth/mock-auth-service.ts:392`, `src/env.core.ts:17`.

В production скрыты кнопки быстрого входа, но обычный вход продолжает принимать общий пароль `demo12345` для seed-пользователей. Контейнер передаёт демо-пароль без проверки окружения, а единственный DATA_SOURCE — mock.

**Проверка:** отдельный тест с `NODE_ENV=production` успешно вошёл в SUPER_ADMIN с демо-паролем.

**Последствие:** публикация этой конфигурации открывает известный административный доступ. SESSION_SECRET защищает подпись cookie, но не устраняет известные учётные данные.

**Исправление:** запретить mock/seed-аутентификацию при клиентском production-запуске; демо-развёртывание разрешать только отдельным явным режимом без клиентских данных. Для реального запуска использовать постоянный Auth и отдельное создание первого администратора.

### F02 · P1 · ADMIN получает SUPER_ADMIN через очередь сброса пароля

**Код:** `src/server/services/admin/outbox-service.ts:15`, `src/server/auth/mock-auth-service.ts:257`, `src/server/auth/mock-auth-service.ts:291`.

Outbox отдаёт все сообщения любому пользователю с `admin.manage`. Публичный сброс пароля SUPER_ADMIN создаёт сообщение с действующим токеном; обычный ADMIN может прочитать его, сменить пароль и войти с ролью SUPER_ADMIN.

**Проверка:** воспроизведена полная цепочка: запрос сброса → чтение сообщения контекстом ADMIN → сброс → вход как SUPER_ADMIN. Старый пароль SUPER_ADMIN не нужен.

Дополнительная поверхность: `AdminClientService.issueTemporaryPassword` (`client-service.ts:279`) проверяет членство получателя в организации, но не его платформенную роль. Пользователь с платформенной ролью и membership также должен быть защищён от сброса пароля нижестоящим администратором.

**Исправление:** разделить клиентские и служебные операции восстановления. Токены восстановления сотрудников, особенно SUPER_ADMIN, не должны попадать в очередь, доступную обычному ADMIN. Проверять роль получателя при выдаче временного пароля; хранить и фильтровать чувствительные сообщения на сервере.

### F03 · P1 · Переназначение карточки смешивает статистику двух клиентов

**Код:** `src/server/repositories/mock/analytics.ts:108`, `src/server/repositories/mock/analytics.ts:130`; та же модель заложена в `docs/supabase/schema.sql:284` и `:917`.

Суточный агрегат индексируется только по `(cardId, date)`. Если карточку в тот же день освободить и назначить другой организации, следующее касание увеличивает существующую строку прежней организации. organizationId, locationId и employeeId существующей строки не меняются.

**Проверка:** после переназначения новое касание увеличило счётчик прежнего клиента на 1, а счётчик нового клиента остался 0. Сырое событие при этом относится к новому клиенту.

**Последствие:** неверные отчёты и раскрытие агрегированной активности между организациями. Перенос карточки между сотрудниками/филиалами внутри дня также оставляет новые касания в старой группе.

**Исправление:** хранить историю назначений и агрегировать по назначению/измерениям с корректным ключом. Смена арендатора не должна дописывать в его старый агрегат. Исправить одновременно mock-реализацию и SQL-модель.

### F04 · P1 · Два платежа сохраняются, подписка продлевается один раз

**Код:** `src/server/services/admin/billing-service.ts:70`.

Чтение подписки, создание платежа и изменение paidUntil выполняются раздельно. Два запроса читают один paidUntil и записывают одинаковую новую дату.

**Проверка:** два одновременных платежа по месяцу создали две записи платежей, но paidUntil увеличился только на один месяц.

Сбой между сохранением платежа и upsert подписки также оставляет несогласованное состояние. Повтор отправки не защищён ключом идемпотентности.

**Исправление:** один транзакционный метод репозитория/RPC: блокировка подписки, проверка ключа операции, создание платежа, продление и журнал. Добавить тесты параллельных платежей и повторной доставки одного запроса.

### F05 · P1 · Сбой агрегирования безвозвратно теряет касание в отчётах

**Код:** `src/server/services/tap-recorder.ts:32`, `src/server/services/tap-recorder.ts:46`.

Событие сохраняется до инкремента суточной статистики. Если инкремент падает, повторная запись видит `created=false` и больше не пытается обновить агрегат.

**Проверка:** искусственный сбой dailyStats.increment, затем повтор того же события: событие сохранено, сумма касаний не увеличилась.

На уровне `/t/[code]` ошибка только логируется; устойчивой очереди повторов нет.

**Исправление:** транзакционно записывать событие и агрегат в одной операции либо использовать устойчивую очередь с подтверждением обработки. Идемпотентность должна покрывать оба изменения.

### F06 · P2 · Ограничение статистики при истёкшей подписке обходится

**Код:** `src/app/(app)/app/cards/page.tsx:20`, `src/features/cards/components/cards-table.tsx:62`, `src/app/(app)/app/employees/page.tsx:51`, `src/app/(app)/app/cards/[id]/page.tsx:57`.

Таблица карточек вообще не проверяет подписку и показывает taps30. На странице сотрудников статистика скрывается флагом showStats, но полные employees передаются клиентскому компоненту. На странице карточки CardActions получает весь detail со stats даже при закрытом StatsGate.

**Проверка:** браузерный тест под владельцем Aru Beauty увидел заблокированный дашборд, затем доступную колонку «Касания за 30 дней» и taps30 в ответе страницы карточек.

**Исправление:** формировать на сервере DTO без статистических полей для истёкшей подписки, применять одинаковое правило ко всем страницам, экспортам и клиентским props. Передавать CardActions только поля для редактирования.

### F07 · P2 · Параллельные запросы обходят лимиты частоты

**Код:** `src/server/services/lead-service.ts:38`; аналогичная схема check → hit есть в авторизации и редиректе.

Проверка лимита и учёт попытки разделены await. Несколько запросов успевают получить разрешение до записи попыток; результат hit не используется для отказа.

**Проверка:** 12 одновременных заявок на один телефон успешно сохранены при лимите 3 за сутки.

**Исправление:** атомарный consume/reserve, который одновременно учитывает попытку и возвращает решение. После перехода на несколько процессов — общее хранилище лимитов. Вход ограничивать до дорогой проверки пароля.

### F08 · P2 · Два владельца могут одновременно удалить друг друга

**Код:** `src/server/services/team-service.ts:170`, `src/server/services/team-service.ts:188`.

Проверка наличия другого OWNER и удаление разделены. Оба запроса видят второго владельца, затем оба удаляют его.

**Проверка:** два параллельных вызова removeMember оставили организацию без OWNER.

**Исправление:** транзакционная операция под блокировкой организации/набора владельцев. Наличие SQL-триггера без соответствующей сериализации само по себе не доказывает защиту от такого конкурентного сценария.

### F09 · P2 · Карточка нового филиала может вести на отзывы другого филиала

**Код:** `src/server/services/admin/card-admin-service.ts:264`.

При отсутствии подтверждённой цели выбранного филиала назначение молча использует `targets[0]` любой другой точки этой организации.

**Проверка:** создан филиал без цели, назначена свободная карточка; она получила target другого филиала.

**Последствие:** гость оставляет отзыв другой точке, а статистика приписывает касание выбранному филиалу.

**Исправление:** требовать явный выбор подходящей цели или оставлять карточку неактивной с понятной причиной. Если общая цель организации нужна, она должна быть явной и иметь locationId=null.

## Дополнительные замечания

### F10 · P2 · «Уникальные посетители» — сумма уникальностей по карточкам и дням

**Код:** `src/features/analytics/visitor-cookie.ts:56`, `src/server/repositories/mock/analytics.ts:42`.

Cookie определяет первый визит отдельно для каждого кода. Один браузер, приложивший две карточки в один день, учитывается дважды в сумме организации. Тот же человек в разные дни также повторно входит в сумму периода. Показатель полезен, но не равен числу разных людей за период.

В интерфейсе есть пояснение о дневном учёте, однако оно не объясняет двойной учёт между карточками. Конверсия наследует эту особенность знаменателя. При фильтре по сотруднику/карточке числитель остаётся приростом отзывов всего связанного филиала.

**Действие:** явно назвать метрику, описать её единицу измерения и ограничить выводы о конверсии отдельных сотрудников. Изменение способа идентификации посетителей — отдельное продуктовое решение, а не обязательное условие MVP.

### F11 · P2 · В production-зависимостях найдены 7 advisory

`pnpm audit --prod --json`: 2 High, 3 Moderate, 2 Low, Critical — 0.

High приходят через установленный в dependencies CLI shadcn: вложенные zod 3.25.76 и body-parser 2.3.0. Прямой zod приложения имеет версию ^4.6.7. Остальные находки относятся к uuid через exceljs и fast-uri через транзитивные цепочки.

Это результат проверки дерева зависимостей; эксплуатация этих пакетов через маршруты приложения не доказана. Импорты shadcn CLI в runtime-коде не обнаружены.

**Действие:** перенести/удалить CLI из production-зависимостей, обновить совместимые транзитивные цепочки и повторить audit. Не подменять zod 3 на 4 глобальным override без проверки совместимости.

Источники: [Zod GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), [body-parser GHSA-27r3-jxmh-p828](https://github.com/advisories/GHSA-27r3-jxmh-p828), [uuid GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq).

## Ограничения текущей версии перед запуском

1. **Данные, пароли, сессии, письма и лимиты находятся в памяти процесса.** После перезапуска изменения теряются, а несколько процессов имеют разные состояния. Это явно описано в README и не скрытая ошибка, но для клиентов является блокером. Код: `src/mocks/db.ts:47`, `src/server/container.ts:70`, `src/server/auth/mock-auth-service.ts:68`.
2. **Реального получения рейтингов/отзывов нет.** `src/config/features.ts:11`; DATA_SOURCE допускает только mock. После подключения API нужны реальные сценарии ошибок, квот, повторов и свежести данных.
3. **Почта ручная, платежи ручные.** Для небольшого пилота это допустимо, если оператор реально обслуживает очередь. Ограничение связано с операционной нагрузкой; автоматизация сама по себе не обязательна для MVP. Восстановление доступа сотрудников требует исправления F02 независимо от способа отправки.
4. **Контакты продления подписки демонстрационные.** `src/config/contacts.ts:6`. Пользователь с истёкшей подпиской сейчас получает фиктивный телефон/WhatsApp.
5. **APP_URL в production может остаться localhost.** `src/env.core.ts:19` проверяет форму URL, но не требует боевой домен. Напечатанные QR/NFC-ссылки и приглашения будут неверными. До изготовления карточек домен должен быть зафиксирован и проверен.
6. **SQL — проект схемы, не применённые миграции.** Положительно, что RLS проверяется PGlite. Это не подтверждает работу реальных Supabase Auth, refresh-cookie и развёрнутой БД. Ошибка агрегатов F03 есть и в SQL-документе.
7. **Обращения не являются перепиской с клиентом.** В кабинете есть создание и список со статусами; комментарии сотрудников внутренние. Для ответа нужен внешний канал либо отдельная функция публичных ответов.
8. **Эксплуатационная готовность ограничена.** В репозитории не найден CI-пайплайн; не проверены резервное копирование, восстановление, мониторинг и нагрузка. Проект содержит полезные security headers и журнал, но они не заменяют эти проверки после подключения реальной БД.

## Сильные стороны кода

- Единая матрица прав используется интерфейсом и сервером; у действий есть Zod и проверки полномочий.
- OrganizationId берётся из проверенного контекста, а tenant-репозитории добавляют фильтр организации по конструкции.
- Архитектурные тесты контролируют границы слоёв и наличие проверок доступа на маршрутах.
- Подписанные httpOnly-сессии, отзыв сессий, scrypt для заданных паролей, случайные одноразовые токены и хранение их хешей.
- Редирект не принимает адрес из query, повторно проверяет подтверждённую цель и allowlist, отдаёт no-store и нейтральные страницы для недоступных карточек.
- Есть CSP с nonce и стандартные защитные заголовки; сырой stack trace не возвращается из Server Actions.
- CSV защищается от формул, даты обрабатываются с часовым поясом, поля имеют ограничения длины.
- Создание клиента/партии и назначение карточек уже вынесены в отдельные атомарные методы репозитория. Такой же подход нужно распространить на платежи, касания и управление владельцами.
- UI включает мобильную навигацию, пустые состояния, подтверждения действий, подписи полей и сообщения об ошибках.
