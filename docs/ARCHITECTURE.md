# Архитектура TapToGo

Документ для разработчика, который впервые открывает код. Здесь описано: какие есть слои, где что лежит, как проходит запрос и как добавить новую фичу. Запуск, демо-аккаунты и команды — в [README](../README.md). Переход на реальные сервисы — в [SUPABASE_MIGRATION.md](SUPABASE_MIGRATION.md).

## Коротко

Одно приложение на Next.js 16 (App Router), три зоны:

| Зона         | URL            | Кто                               |
| ------------ | -------------- | --------------------------------- |
| Публичная    | `/`, `/login`… | все                               |
| Кабинет      | `/app/*`       | клиенты: OWNER, MANAGER           |
| Админ-панель | `/admin/*`     | администраторы TapToGo: ADMIN     |
| Редирект     | `/t/{code}`    | гости, которые приложили карточку |

Данные сейчас живут в памяти процесса: при старте их генерирует `src/mocks/seed.ts`. Всё, что зависит от внешнего мира (БД, вход, почта, файлы, 2ГИС, лимиты), спрятано за интерфейсами. Реализации выбирает **одно место** — `src/server/container.ts`.

## Слои

```
 Браузер
   │  (только HTML/RSC и вызовы Server Actions — к БД и внешним API браузер не ходит)
   ▼
 app/ ─ страницы, layout'ы, route handlers           ← маршруты и проверка доступа
   │
 features/<фича>/actions.ts ─ Server Actions         ← Zod → права → сервис
   │
 server/services/ ─ бизнес-логика                    ← правила продукта, журнал
   │
 server/container.ts ─ выбор реализаций
   ├── repositories/  (интерфейсы)   → repositories/mock/  | позже supabase/
   ├── auth/          AuthService    → MockAuthService     | позже Supabase Auth
   ├── providers/     email (ручная очередь), reviews (2ГИС)
   └── security/      RateLimiter
```

Правила, которые держат слои раздельными:

1. **Моки импортирует только `container.ts`.** ESLint (`no-restricted-imports` в `eslint.config.mjs`) запрещает импорт `@/mocks` и `server/**/mock` в любом другом файле. Исключение — тесты.
2. **Сервисы знают только интерфейсы.** Они получают `Repositories` и провайдеры через конструктор, а не импортом. Поэтому сервис можно протестировать на моках и без изменений запустить на Supabase.
3. **Всё серверное помечено `import "server-only"`.** Случайный импорт в клиентский компонент сломает сборку, а не выдаст секрет в браузер.
4. **Организация берётся только из сессии.** `OrgContext` (`server/services/context.ts`) строится из проверенной сессии функцией `orgContextFrom`. В формах нет поля `organizationId`, а если его подставить, оно игнорируется.
5. **Сервисы кабинета видят данные только своей организации.** Они работают не с `Repositories` напрямую, а с видом `forOrganization(repositories, organizationId)` (`server/repositories/tenant.ts`), где фильтр по организации вшит в каждый метод. Забыть его нельзя — это проверяет архитектурный тест.
6. **Права проверяются дважды.** Действие проверяет право до вызова сервиса, а сервис — ещё раз внутри (`assertOrgPermission`, `assertAdmin`). Вызов сервиса с другого пути (новая страница, cron) не обойдёт проверку.
7. **Страницы и маршруты не ходят в репозитории.** Только в сервисы (проверяет архитектурный тест). Исключение — dev-страница `/dev/data` и сам редирект `/t/{code}`, которому нужен системный доступ без сервисов.

### Правила работы с данными

Эти правила делают так, чтобы код, работающий на моках, работал и на Supabase с ростом числа клиентов:

- **Статистику читают суммами, а не строками.** `dailyStats.total` и `dailyStats.totalsBy(dimension)` — это `sum … group by` в БД. Объём ответа зависит от числа дней или карточек в отчёте, а не от «карточки × дни».
- **Платформенные списки ограничены.** Поиск карточек в админке отдаёт не больше 500 строк и общее число; обращения, лиды и платежи — последние 100. Счётчики (`count`, `countBy`) не загружают строки.
- **Много объектов — один запрос.** Поиск по списку id или кодов — `findByIds`/`findByCodes`, комментарии для страницы — `listFor`, журнал для пачки — `recordMany`. Запрос в цикле по элементам — ошибка.
- **Многошаговые записи атомарны.** Создание клиента, партии с карточками и назначение карточек — по одному методу репозитория, который в Supabase становится одной SQL-функцией (`create_client`, `create_batch_with_cards`, `assign_cards`). Назначение заново проверяет «карточка ещё свободна» и лимит тарифа под блокировкой строк, поэтому два админа не отдадут одну карточку двум клиентам.
- **Внешние побочные эффекты не откатывают сохранённое.** Если письмо не ушло, приглашение уже сохранено; пользователь видит предупреждение и может отправить его повторно.

## Как проходит запрос

### Страница

```ts
export default async function EmployeesPage({ searchParams }: PageProps<"/app/employees">) {
  const access = await requireOrgAccess("org.view"); // нет сессии → /login, нет права → 403
  const ctx = orgContextFrom(access);                 // организация — из сессии
  const employees = await getServices().employees.list(ctx, period);
  …
}
```

- `proxy.ts` до рендера отсекает явно анонимных: без cookie сессии `/app` и `/admin` ведут на `/login?next=…`. Это только оптимизация, **не защита**.
- Защита — `requireOrgAccess(permission)` / `requirePlatformAccess(permission)` в начале **каждой** страницы и route handler. Они проверяют подпись и срок сессии, статус пользователя, membership в активной организации и право по матрице. Без права — `forbidden()`, это страница 403.
- Чужой id в URL не находится: репозитории получают `OrgScope`, и строки других организаций для них невидимы. Ответ — 404, а не 403, чтобы не раскрывать, что такой объект существует.

### Server Action

Каждое изменение данных проходит один конвейер:

```ts
export async function createEmployeeAction(input: EmployeeFormInput): Promise<ActionResult> {
  return runOrgAction("org.employees.manage", createEmployeeSchema, input, async (ctx, data) => {
    await getServices().employees.create(ctx, data);
    return null;
  });
}
```

1. **Zod.** Невалидный ввод → `{ ok: false, error: { code: "VALIDATION", fieldErrors } }`. Ошибки раскладываются по полям формы (`applyActionError` из `lib/forms.ts`).
2. **Права.** Те же проверки, что у страниц, плюс запрет любых изменений в режиме просмотра кабинета сотрудником платформы.
3. **Сервис.** Ошибки бизнес-правил — `serviceError(code, key)` с текстом из словаря (`serverErrors`). Любое другое исключение превращается в `INTERNAL` с коротким кодом для поиска в логе. Stack trace клиенту не уходит.
4. **`refresh()`.** Текущая страница перерисовывается с новыми данными.

В админ-панели то же самое делает `runAdminAction` с правами платформы. Публичные формы (заявка, вход) используют `runAction` напрямую: вместо проверки прав у них лимит частоты.

### Редирект `/t/{code}`

Самый нагруженный путь, поэтому он сделан route handler'ом без React:

1. Код проверяется регуляркой, затем лимит 60 запросов в минуту с IP.
2. Карточка, цель и организация читаются через `systemRepositories`: гость анонимен.
3. URL берётся **только** из сохранённой подтверждённой цели и повторно проверяется по allowlist доменов. Параметры запроса не влияют на адрес.
4. Ответ `302` отправляется сразу. Касание записывается после ответа (`after()`), и ошибка записи редирект не ломает.
5. В событии касания нет IP, User-Agent и идентификатора посетителя. Дубли и уникальных посетителей определяет cookie `ttg_seen` на телефоне гостя.

### Две роли доступа к данным

В контейнере два набора репозиториев:

- `repositories` — от имени вошедшего пользователя. В Supabase под ним клиент с JWT пользователя, и действует RLS.
- `systemRepositories` — для потоков без пользователя: редирект и касания, заявки с лендинга, вход и приглашения, cron. В Supabase под ним service-ключ.

Сейчас это один и тот же объект в памяти. Разделение заложено заранее, чтобы при переходе на Supabase не искать по коду, где нужен какой доступ.

## Даты и время

- Моменты времени хранятся в UTC (ISO-строка с `Z`).
- Календарные даты (статистика по дням, «оплачено до») — строки `YYYY-MM-DD` в часовом поясе **организации** (по умолчанию `Asia/Almaty`).
- Перевод между ними — только через `lib/dates.ts` (`toLocalDate`, `addDays`, …, на `@date-fns/tz`).
- Форматирование для экрана — `lib/format.ts` с явным часовым поясом. Так сервер и браузер всегда показывают одно и то же.

## Тексты и языки

- Все строки интерфейса, ошибок и писем лежат в `src/i18n/messages/ru.json`. Ключи типизированы: опечатка в ключе — ошибка компиляции.
- Как добавить казахский — в комментарии `src/i18n/config.ts`.

## Как добавить новую фичу

Пример: владелец хочет оставлять **заметки к карточке**.

1. **Модель.** Создать `features/card-notes/schemas.ts` с Zod-схемой сущности (`cardNoteSchema`) и выведенным типом. Ограничить длину каждой строки.
2. **Репозиторий.** Добавить интерфейс `CardNoteRepository` в `server/repositories/` и поле в тип `Repositories`. Все методы асинхронные. Методы для данных арендатора принимают `scope?: OrgScope`. Добавить нужные методы в вид на организацию `forOrganization` (`repositories/tenant.ts`) с уже подставленной организацией. Списки, которые растут со временем, — с `limit`.
3. **Мок.** Реализовать его в `server/repositories/mock/`: таблица в `mocks/db.ts`, по желанию демо-строки в `mocks/seed.ts`. Тест — в `mock-repositories.test.ts`.
4. **Схема БД.** Добавить таблицу, индексы и RLS-политики в `docs/supabase/schema.sql`, а проверку политик — в `tests/schema/rls.test.ts`. Так черновик не отстанет от кода.
5. **Право.** Если существующих прав не хватает, добавить новое в `server/permissions.ts` (например, `org.notes.manage`) и обновить тест матрицы.
6. **Сервис.** Создать `server/services/card-note-service.ts`. Методы принимают `ctx: OrgContext` и работают через `forOrganization(this.repositories, ctx.organizationId)`. Методы записи начинаются с `assertOrgPermission(ctx, "org.notes.manage")`. Изменения пишутся в журнал (`audit.record`). Подключить сервис в `createServices` (`server/services/index.ts`), добавить его в список сервисов кабинета в `server/architecture.test.ts` и покрыть unit-тестом, в том числе на изоляцию: чужая карточка не находится.
7. **Форма и действие.** Схема формы — в `form-schemas.ts`, Server Action — в `actions.ts` через `runOrgAction(permission, schema, input, handler)`.
8. **UI.** Компоненты — в `features/card-notes/components/`. Тексты — в `ru.json`. Кнопки показываются по `can(...)` или по списку прав, пришедшему со страницы, но проверка всё равно на сервере.
9. **Страница.** В `app/(app)/app/...` первой строкой `requireOrgAccess(...)`.
10. **e2e** для главного сценария — в `tests/e2e/`.

Проверка перед сдачей: `pnpm check` (линт, типы, unit) и `pnpm test:e2e`.

## Тесты

| Уровень  | Где                                          | Что проверяем                                                                |
| -------- | -------------------------------------------- | ---------------------------------------------------------------------------- |
| Unit     | `src/**/*.test.ts` (Vitest)                  | схемы, права, сервисы на моках, seed, утилиты                                |
| e2e      | `tests/e2e/*.spec.ts` (Playwright)           | сценарии по ролям на **production-сборке**, desktop и мобильный              |
| Схема БД | `tests/schema/rls.test.ts` (Vitest + PGlite) | `schema.sql` выполняется, RLS и триггеры пускают каждую роль ровно куда надо |

e2e запускаются на production-сборке намеренно: так проверяются те же заголовки безопасности и CSP без `unsafe-eval`, что поедут на сервер. Мок-данные общие для всех тестов. Тесты, которые меняют данные, выполняются только в desktop-проекте (`test.skip(isMobile, …)`) и создают объекты с уникальными именами.

## Решения, которые стоит знать

- **`cacheComponents` выключен.** CSP с nonce несовместим с предрендером (PPR): nonce должен быть уникален для каждого запроса, поэтому страницы рендерятся динамически.
- **`proxy.ts` вместо `middleware.ts`.** Это новое имя в Next.js 16.
- **Подписка не влияет на редирект.** Гости клиента с истёкшей подпиской всё равно попадают на страницу отзывов. Скрывается только статистика в кабинете.
- **Статус подписки вычисляется** из `paidUntil` и grace-периода (`features/subscriptions/status.ts`), а не хранится.
- **Сводка по дням** (`DailyCardStat`) обновляется при каждом касании. Графики строятся по ней, а сырые события нужны тепловой карте и разбивкам.
